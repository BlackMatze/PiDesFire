# PiDesFire Card Layout

## Phase 1 Scope

This layout is for the Raspberry Pi provisioner repository only. The door reader is implemented separately and must authenticate against the same on-card application and key scheme.

## Security Goals

- Card credentials must not be copyable through UID-only cloning.
- Reader trust must require DESFire EV3 mutual authentication.
- Home Assistant remains the only authorization authority.
- Time-based access rules are never stored on the card.

## Application Layout

### DESFire application

- AID: `D15F01`
- One application per access system
- AES keys only

### Application keys

#### Key 0: application master key

- Used for administrative operations
- Used during provisioning and key rotation

#### Key 1: reader authentication key

- Used by the door reader to authenticate before reading card identity data
- Diversified per card

#### Key 2: provisioner service key

- Used by the Pi-side provisioner for maintenance and recovery flows
- Separate from the reader key

## Files

### File 01: identity record

- Type: standard data file
- Access: readable only after successful authentication with Key 1
- Size: 32 bytes

#### Binary layout

| Offset | Size | Field | Description |
| --- | --- | --- | --- |
| 0 | 1 | format_version | Layout version, initial value `0x01` |
| 1 | 16 | card_uuid | Random 16-byte card identifier generated by the provisioner |
| 17 | 4 | issue_counter | Big-endian credential generation counter |
| 21 | 1 | flags | Reserved for future operational markers |
| 22 | 10 | reserved | Reserved, write zero for now |

### File 02: metadata record

- Type: standard data file
- Access: administrative only, intended for Key 0 or Key 2
- Size: 32 bytes
- Optional in the first working milestone, but reserved now for forward compatibility

#### Suggested contents

- issuer or site identifier
- provisioning batch or timestamp marker
- diversification scheme version
- reserved bytes for migration metadata

## Identity Model

- The on-card identity is the `card_uuid`, not the NFC UID.
- Each physical card gets a new random `card_uuid`.
- Reissued cards should get a new `card_uuid` rather than reusing an old one.
- Person-to-card mapping is maintained in Home Assistant.

## Key Diversification

Key 1 must be diversified per card using a site master secret and card-specific inputs.

Recommended diversification inputs:

- NFC UID
- DESFire AID
- card_uuid

Using the UID as one diversification input is acceptable because access is still gated by DESFire authentication, not by UID trust.

## Reader Contract

The reader-side implementation must:

1. Detect the card.
2. Select AID `D15F01`.
3. Authenticate with diversified Key 1.
4. Read File 01.
5. Report `card_uuid`, `issue_counter`, and `reader_id` to Home Assistant.

## Provisioner Contract

The Pi-side provisioner must:

1. Create or select the application.
2. Set Key 0, Key 1, and Key 2.
3. Create File 01 and optionally File 02.
4. Write the identity record.
5. Read back and verify the written data.
6. Register the `card_uuid` in Home Assistant.
